# 流水线各阶段详细流程与质量门禁

## 阶段 0：init（总编）

1. 解析用户创意：题材、卖点、目标篇幅、风格偏好、更新诉求，以及三类硬约束——小说类型（`type_tags`）、语言风格（`style_constraints`）、时间线宏观锚点（`timeline_constraints`）。信息不足时**只问一轮**，集中提问（篇幅档位、批次大小、美术模式与范围、类型与语言风格未明维度），其余合理默认（类型按题材推断、人称默认第三人称限知、语体默认现代白话并在计划中注明）。硬约束取值口径见 [constraints.md](constraints.md)。
2. 创建工作区目录与 v2 `project.yaml`（按模板填写硬约束、`art_scope`），`stage: planning`。只有总编可写本文件。

篇幅档位默认值：

| 档位 | 总章数 | 章均字数 | batch_size |
|------|--------|----------|------------|
| 短篇 | ≤10 | 2000–3000 | 不分批（一批完成） |
| 中篇 | 11–40 | 2500–3500 | 5 |
| 长篇 | 41–200 | 3000–4000 | 5 |
| 超长篇 | >200 | 3000–4000 | 10，且按卷分期立项 |

## 阶段 1：planning（总编）

产出 `01-planning/plan.md`：作品定位、**硬约束（类型/语言风格/时间线宏观锚点）**、各阶段任务分派、批次划分、汇报节点、风险与应对。
**门禁**：将计划要点（含类型、语言风格、时间线、美术模式与范围）汇报用户并获确认，三类硬约束与 `art_scope` 已写入 `project.yaml`（自动化/无人值守场景下，用户已在最初指令中给足约束时可视为预确认，但须在汇报中说明采用值）。

## 阶段 2：architecture（架构师）

顺序产出：`world.md` → `synopsis.md` → `outline.md`。
**门禁**（总编核验）：

- [ ] 世界观无内在矛盾，力量/规则体系有明确边界与代价
- [ ] world.md 已确立计时/纪年体系，且与 `type_tags` 设定边界一致（如穿越类交代穿越机制、现实类无超自然金手指）
- [ ] 梗概含完整起承转合与结局，主线闭环；已填故事总时间跨度与分幕时间推进
- [ ] 中短篇及普通长篇的大纲覆盖全部章节；超长篇完成全书卷级大纲与当前卷逐章大纲，并写明后续卷在开工前补齐
- [ ] 三份文档均未违背 `project.yaml` 的类型与语言风格硬约束
- [ ] 伏笔表完整：每条伏笔有埋设章与回收章

## 阶段 3：lore（设定师）

基于大纲产出 `03-lore/` 设定卡。
**门禁**（总编核验）：

- [ ] 主角、反派、所有戏份≥3章的配角均有人物卡
- [ ] 主线任务与各支线有任务卡，与大纲章节对应
- [ ] 大纲中出现的关键场景、关键道具、关键情节均有卡
- [ ] 卡内信息与 world/synopsis/outline 无冲突
- [ ] `03-lore/index.md` 索引覆盖全部卡片

设定卡可按类别并行，但并行子代理只能写各自卡片，不得同时修改 `index.md`。全部子任务返回后，由一个指定设定师统一生成并校验索引。

## 阶段 4–5：drafting / editing 分批循环

每批流程（批大小 = `project.yaml.batch_size`）：

1. **总编**更新 `progress.current_batch`、`stage: drafting` 与本批 `status: drafting`，按 task-brief 模板列出本批章节与对应大纲、设定卡清单；第二批起另列当前批次前最近 5 章定稿（不足 5 章则列出全部已有定稿）。
2. **写手**逐章起草至 `04-drafts/batch-NN/`，每章自检（字数、钩子、视角）后交接。
3. **总编**核验初稿后更新 `stage: editing`、本批 `status: editing`，再交编辑。
4. **编辑**逐章润色对齐，定稿入 `05-final/`，按模板写修订记录；发现设定冲突报总编。定稿后**增量更新前情提要** `05-final/story-so-far.md`（每批新增 200–400 字）。
5. **总编**写 `reports/batch-NN-report.md`，更新本批 `status: reported` 与 `reported_at`，再向用户汇报。
6. **用户确认**后由总编更新 `status: approved` 与 `approved_at`。未批准前不得新建或启动下一批；用户要求调整时：登记 decision → 指派上游/正文返工 → 重新汇报。

**门禁**：批内每章通过编辑的一致性核对清单（见 `novel-editor` 技能，含时间线台账核对与风格约束核对）；前情提要已更新至本批末章（含"当前故事时间"）。

**卷级归档（超长篇）**：每卷最后一批获用户确认后，总编写 `reports/volume-N-report.md`（按模板）。下一卷开工时，各角色以"卷报告 + 前情提要"替代逐批报告回溯。

## 阶段 6：art（设计师）

覆盖范围以 `art_scope` 为准，不再默认要求为所有关键情节出图。设计任务仅在输出路径完全不同的情况下并行。

- `art_enabled: false`：总编设置 `progress.art.status: skipped`；最终批获批准后直接进入 `acceptance`。
- `art_mode: final`：最终批获批准后进入 `stage: art`，完成后设置 `progress.art.status: complete`。
- `art_mode: incremental`：每批定稿后可制作该批物料，使用独立 `progress.art` 记录，不改变当前正文 `stage`；最终批获批准时，若美术已完成则进入 `acceptance`，否则进入 `art` 补齐。

**门禁**（总编核验）：

- [ ] `art_scope.cover: true` 时有封面规格文档 1 份
- [ ] 立绘与插画覆盖 `art_scope` 指定对象
- [ ] 形象描述与人物卡/场景卡一致（发色、服饰、标志物等）

## 阶段 7：acceptance（总编）

1. 按交付清单逐项核对：全章定稿、字数总计、设定文档、美术物料、修订记录。
2. 按 templates/final-report.md 产出 `reports/final-report.md`：作品简介、数据统计、目录、文件索引、遗留事项。
3. 向用户交付，`stage: delivered`。

## 状态转换规则

- 正文批次只允许 `pending → drafting → editing → reported → approved`；返工可从 `reported` 回到 `drafting` 或 `editing`，并须有 decision/issue 记录。
- `stage` 表示主流水线当前位置；增量美术只写 `progress.art`，不得把正在写作的项目切到 `stage: art`。
- 所有 `stage`、批次状态、时间戳、decisions 与 issues 只由总编写入 `project.yaml`。其他角色在返回摘要的 `state_updates` 中提出建议。

## 中断恢复

任何角色启动时：读 `project.yaml` → 确定 stage、current_batch、批次状态与美术状态 → 检查该阶段产物完整性（半成品文件以实际内容为准补齐）→ 从断点继续。不重做已过门禁的阶段。

缺少 `schema_version` 时按 v1 兼容读取：从 plan/world/synopsis 恢复时间线，从旧 `art_enabled`/`art_mode` 推导美术范围。总编在下一次状态更新时补齐 v2 字段并登记 migration decision；其他角色不得代为迁移。

## 上下文管理纪律（所有角色遵守）

长篇项目的会话上下文必然装不下全书，按以下纪律工作：

1. **不读全文**：恢复剧情记忆的顺序是 前情提要（`05-final/story-so-far.md`）→ 设定卡索引（`03-lore/index.md`）→ 按需打开具体卡/章节，禁止为"找回感觉"通读已写正文。
2. **摘要替代原文**：跨卷回溯读卷报告（`reports/volume-N-report.md`），不读逐批报告；查人物/道具当前状态看索引与卡上轨迹，不翻正文。
3. **批末即断点**：每批汇报节点是推荐的会话切换点；总编汇报后即可结束会话，下次从 `project.yaml` 断点恢复。
4. **任务单要窄**：总编派活时明确列出"只需读这些文件"，被派角色不自行扩大阅读范围。写手批次任务的前序正文固定为当前批次前最近 5 章定稿；已有定稿不足 5 章时全部读取，第一批不读前序正文。
