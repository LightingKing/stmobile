# 小说工程与反馈修订工作流

## 目录

- 使用场景与落盘边界
- 进入已有项目与推荐目录
- 设定状态与反馈同步
- 单一事实源
- 版本与验证

## 使用场景

在新建、重建或持续维护十万字以上小说项目时使用；在用户修正定义、确认方案或要求同步全局设定时再次使用。

## 一、先判断是否需要落盘

- 用户只要求解释、评估或诊断：读取项目并给出证据，不修改文件。
- 用户要求创建、整理、修改、续写或同步：更新文件，并做与风险相称的验证。
- 用户只给出一条补充设定：判断其影响面；不要为一条局部反馈重写无关文件。

## 二、进入已有项目

按以下顺序盘点：

1. 读取工作区规则、项目首页和创作纲领。
2. 找到设定状态、时间线、术语表、人物索引、结构索引和正文索引。
3. 检查现有目录、版本状态和用户未提交修改。
4. 搜索本轮关键词及其同义词、旧称和反义分类。
5. 识别单一事实源，不在多个文件中维护互相竞争的最终版本。

保护用户原稿。未经明确授权，不删除、覆盖或大规模改写已有正文；需要迁移时保留归档和迁移说明。

## 三、推荐目录

只在用户需要文件化长篇工程时创建，已有结构可复用，不强制改名。

```text
00-项目管理/
  创作纲领.md
  设定状态与版本规则.md
  术语表.md
  连续性台账.md
  待决问题.md
01-世界观/
  时间线、社会、经济、政治、地点、组织/
02-科技设定/
  技术树、单项技术、科学依据与限制/
03-人物设定/
  人物索引、个人档案、关系与伤亡台账/
04-故事结构/
  总纲、分卷、故事线、伏笔、视角与汇流/
05-正文/
  00-正文索引.md
  第一卷/、第二卷/……
06-素材与研究/
  科学来源、研究问题、事实核验/
99-归档/
```

## 四、设定状态

统一使用以下状态，或映射到项目已有状态：

- `已定`：用户明确确认，或已经进入不可轻易改动的正文事实。
- `暂定`：为推进工作而补全，允许替换。
- `待确认`：不同答案会实质改变人物、世界或结局，需要用户决定。
- `废弃`：已被用户修正或因科学、连续性问题不再使用。

最新的用户明确修正优先于较早草案。不要把“作者建议”自动升级为“已定”。

## 五、反馈同步算法

收到反馈后依次执行：

1. 提炼新事实：用户究竟确认、否定或重定义了什么？
2. 记录旧事实：旧定义出现在哪里，是否已进入正文？
3. 列出影响域：术语、世界观、科技、人物、组织、时间线、总纲、章节、索引。
4. 搜索所有旧称、缩写、近义词和隐含描述。
5. 更新单一事实源，再更新依赖文件。
6. 对无法自动决定的情节后果建立待确认项。
7. 检查是否仍有新旧定义混用。
8. 在连续性台账记录重大语义迁移。

定义变化尤其要检查“相邻类别”。例如把某群体从生物增强者改为具身机器人时，要同步人口分类、权利体系、医疗与维修、死亡定义、劳动关系和角色背景。

## 六、单一事实源

为下列领域各指定一个主文件：

| 事实类型 | 推荐主文件 |
|---|---|
| 年份、事件顺序 | 历史时间线 |
| 技术能力、限制 | 对应科技设定 |
| 年龄、身份、弧光 | 人物个人档案 |
| 正式名称、分类 | 术语表或分类总览 |
| 卷章顺序 | 分卷结构或章节索引 |
| 伏笔状态 | 伏笔与回收台账 |

其他文件可以摘要或链接，不要复制一整套容易漂移的数据。

## 七、版本与验证

重大更新后检查：

- 年份与年龄能否同时成立
- 同一组织、技术和人物是否存在多个正式名称
- 技术是否在成熟之前被人物使用
- 人物是否知道其视角不可能知道的信息
- 死亡、离场、创伤和责任是否在后续章节留下影响
- 索引、相对链接和文件路径是否有效
- 用户原稿和无关修改是否保持不变

只在用户明确要求时进行版本提交、远程推送或发布；不要把文件修改授权扩展为外部发布授权。
